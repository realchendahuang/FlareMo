## 0. 设计动机与核心决策

### 0.1 真实痛点
1. **入口割裂，两套心智**：
   - 记录在主页 composer，文章藏在侧栏「文章」二级列表的「写文章」按钮里；
   - 用户打开应用想“写点什么”，被迫先在心里做一次分类判断；甚至产生“找不到在哪写文章”的实际困扰。
2. **灵感演进被粗暴打断**：
   - 真实的创作往往源于“随手在小框敲了两句话”，越写越长，产生了公开发表的诉求；
   - 现存流程下，用户必须全选复制、关掉输入框、点侧边栏、进文章页、新建、粘贴，心流被完全破坏。

### 0.2 核心定案
1. **一个入口（One Composer）**：
   - 主页 composer 是用户唯一需要认识的书写起点。
   - 小尺寸 composer **不做任何打扰**：不加文章类型选项，不加长文复杂控件，保证碎片速记（Capture）的毫秒级纯粹性。
2. **原位升维：专注画布（Focus Canvas）而非弹窗或路由跳转**：
   - 点击底栏右侧「放大」按钮（`Maximize2Icon`），当前输入框原位舒展为全视口专注画布；
   - 不是传统冷冰冰的打断式对话框（Modal Dialog），没有沉重的黑蒙层；也不是重载路由跳转，保持 SPA 即时感与上下文连贯；
   - 随时按 `Esc` 或点击收起，面板轻盈合拢，草稿一个字符不丢。
3. **诚实的心智演进：起草 $\to$ 工坊**：
   - 画布默认依然是「记录」，支持直接发送长记录；
   - 用户选「文章」时，画布定位为**「文章起草台」**；右下角主按钮明确为 **「进入文章排版 →」**；
   - 点击后后台完成附件认领与草稿落库，无缝推进至独立的 `/articles/:id/edit`（文章工坊）完成深度排版与公开发布门，彻底消除“全屏跳全屏”的心理落差。

## 1. 交互形态架构：为什么是「专注画布」？

在形态选择上，对比三种技术与交互路径：

```
[方案 A: 路由跳转 /compose]  ──> 太重：打断主页仪表盘心流，写完还要回跳，破坏 SPA 流动感。
[方案 B: 居中对话框 Modal]   ──> 太挤：周围一圈黑蒙层，心理暗示为“填表/确认”，压抑长文呼吸。
[方案 C: 专注画布 Focus Canvas] ──> 推荐：原位展开，全视口纸张隐喻，轻盈收退，草稿零丢失。
```

### 1.1 视觉规范与材质（遵循 Ember 规范）
- **外层覆盖**：
  - 不使用重度变暗的黑色 Backdrop（`bg-black/80` 属于放肆设计）；
  - 使用应用标准暖调背景 `bg-background`，在桌面端配合极轻微的 Backdrop Glass 材质（`backdrop-blur-xs bg-background/95`），整体感觉如同“在主页上方轻轻铺开一张纯净的大信纸”。
- **居中信纸约束**：
  - 严禁正文宽度直接撑满宽屏（超过 800px 会导致眼球横向移动疲劳）；
  - 核心书写区域采用 `max-w-3xl`（约 768px）居中收敛，两侧保留充足的呼吸留白，打造沉浸式打字机氛围。
- **动效编排**：
  - 入场：`motion-safe:animate-rise`（200ms expo 展开），编辑器内容平滑延续；
  - 退场：`motion-safe:animate-fade`（140ms 平滑收起），焦点无缝归还至小框末尾。

## 2. 界面空间布局与组件拆解

```
+-----------------------------------------------------------------------------------+
|  [Logo / 状态微标: 已保存 842 字]                         [Esc 收起 ⤓] [X 关闭]   |  <- 顶部状态行
+-----------------------------------------------------------------------------------+
|                                                                                   |
|  [ 文章标题输入框（仅文章模式显示，大号字，无边框）                            ]  |  <- 标题区
|  ───────────────────────────────────────────────────────────────────────────────  |
|                                                                                   |
|  正文编辑器（TipTap）                                                             |  <- 核心画布区
|  - 记录模式：常规段落 + 任务列表 + 标签                                           |
|  - 文章模式：启用 buildArticleExtensions（H1-H4、代码高亮、表格、图片内联）      |
|                                                                                   |
|                                                                                   |
+-----------------------------------------------------------------------------------+
|  [#] [图] [列表] [序] [待] [日期] [语音]        [类型: 记录 ▾] [团队 ▾]  [ (↑) 发送 ] |  <- 底部操作行
+-----------------------------------------------------------------------------------+
```

### 2.1 顶部状态栏（Header Rail）
- **左侧：安静的状态指示**
  - 展示字数计数器（`text-xs text-muted-foreground`，如 `842 字`）；
  - 图片上传或同步中时，展示低饱和度微标（`正在上传附件…` / `已实时保存`），不侵扰视线。
- **右侧：收起控制器**
  - 提供 `Minimize2Icon` 收起按钮，附带 Tooltip：`收起 (Esc)`；
  - 点击或按 `Esc`，画布平滑收缩回小尺寸 composer，保留所有编辑状态。

### 2.2 标题输入层（Title Layer）
- **按需显隐**：
  - 当类型为「记录」时：**完全不渲染**。这是 FlareMo 概念模型的红线（记录以时间为骨，没有标题）。
  - 当类型为「文章」时：优雅淡入。
- **视觉风格**：
  - 采用无边框设计：`text-xl sm:text-2xl font-semibold tracking-tight placeholder:text-muted-foreground/50 border-0 focus-visible:ring-0 px-0`；
  - 占位符文案：`文章标题…`；留空合法（发布门才会强制非空验证）。

### 2.3 正文编辑层（Body Layer）
- **纯粹的 Markdown 契约**：
  - 切换「记录」与「文章」类型时，TipTap 挂载对应的扩展包（记录为轻量扩展集，文章为 `buildArticleExtensions`）；
  - 切换过程不发生数据丢失：Markdown 文本字符串作为唯一真理，通过 React State / Ref 瞬时交接；
  - 记录模式下支持回车或快捷键提交；文章模式下禁用单纯回车发送（`submitOnEnter={false}`），避免长文段落换行误触发。

### 2.4 底部操作行（Action Rail）
- **左侧：同构工具栏（Toolbar）**：
  - 保持与常驻小框完全一致的按钮序列（#标签、图片/附件、无序列表、有序列表、任务列表、插入日期、语音速记）；
  - 用户的操作直觉与肌肉记忆零成本复用。
- **右侧：意图分流核心（The Splitter）**：
  1. **类型选择 Chip（Dropdown Menu）**：
     - 外观对齐现有的 `ComposerVisibilityMenu` 胶囊风格（`rounded-full border px-2.5 h-7 text-xs`）；
     - 默认状态：`记录 · 发到时间线`（图标：`ClockIcon` 或 `MessageSquareIcon`）；
     - 切换选项：`文章 · 公开可收录`（图标：`BookOpenIcon` 或 `FileTextIcon`）。
  2. **可见性 Chip（个人 / 团队）**：
     - **互斥规则**：仅在当前类型为「记录」且账户具备团队时显示；
     - **选「文章」时自动隐藏**：文章是面向外部公开发表的独立实体，现阶段不具备团队空间概念，隐藏互斥选项防止心智冲突。
  3. **主行动按钮（Primary Action CTA）**：
     - **类型为「记录」时**：
       - 展示经典的 Ember 品牌渐变圆形发送按钮（`SendIcon`）；
       - 点击或按 `Cmd/Ctrl + Enter`：调用 `createMemoWithAttachments`，执行乐观插入与离线同步，面板轻盈收起回到主页时间线。
     - **类型为「文章」时**：
       - 变形为圆角长胶囊按钮，文案为：**`进入文章排版 →`**（`Button variant="brand"`，带小箭头图标）；
       - 点击或按 `Cmd/Ctrl + Enter`：触发文章起草链路。

## 3. 四大核心用户旅程与状态机（User Flows）

```
[场景 1: 随手碎片] ────> 主页小框敲两句 ────> 回车发送 ────> 纸片入库（快路径零干扰）
                               │
                          (写长了/想放大)
                               │
                               ▼
[场景 2: 专注记录] ────> 点击 ⤢ 放大 ────> 进入专注画布 ────> 敲完长记录 ────> 点发送 ────> 缩回主页
                               │
                           (想公开发表)
                               │
                               ▼
[场景 3: 起草文章] ────> 切为「文章」 ────> 填标题 ────> 点「进入文章排版 →」 ────> 进文章工坊
                               │
                           (反悔/犹豫)
                               │
                               ▼
[场景 4: 随时撤回] ────> 按 Esc 或收起 ────> 原位缩回小框 ────> 草稿完整无损
```

### 旅程 1：日常极速捕捉（Capture Fast-path）
- 用户打开 FlareMo，光标自动聚焦在主页小框；
- 敲下：“今天阅读了关于分布式时钟的论文…”；
- 敲击 `Cmd + Enter` 或点击圆形发送钮；
- 耗时 3 秒，完成记录。整个过程完全感知不到“文章”概念的存在，没有多余的按钮，认知负担为零。

### 旅程 2：碎片演变为长记录（Memo Focus Mode）
- 用户在小框写了 5 行字，觉得小框上下滚动太局促；
- 顺手点击底栏左侧工具栏最右的 `⤢`（全屏放大）；
- 屏幕丝滑铺展为大信纸，字迹完好，光标在末尾闪烁；
- 用户一口气写完 800 字的读书札记；
- 底部类型保持默认的「记录」，点击发送；
- 画布优雅关闭，时间线顶部出现刚写好的长记录卡片。

### 旅程 3：从想法起草到正式文章（Drafting to Publishing）
- 用户在全屏画布里写完一段深刻的技术分析，意识到：“这不应该只是一条个人记录，它值得被搜索引擎收录并公开发表”；
- 用户点击右下角类型 Chip，从「记录」切为「文章」；
- 界面产生温和但清晰的变化：
  - 顶部浮现出标题输入框，用户键入：“浅谈 Cloudflare D1 的强一致性边界”；
  - 右侧的「个人/团队」Chip 自动静默退场；
  - 底部右侧主按钮转变为 **`进入文章排版 →`**；
- 用户点击该按钮：
  - 按钮出现轻微 Loading 状态；
  - 系统首先上传任何未绑定的图片/附件；
  - 拼接正文与附件引用，调用 `POST /api/app/articles` 完成草稿创建与附件认领；
  - 画布关闭，页面无缝平滑进入 `/articles/:id/edit`；
  - 用户在文章工坊里查看 Shiki 代码高亮、调整 slug、填写 SEO 描述并正式发布。
  - 主页 composer 草稿安全释放清空。

### 旅程 4：反悔与安全退出（Frictionless Abort）
- 用户在全屏画布写了一半，或者切到文章后又觉得不够成熟；
- 用户按下键盘 `Esc` 或点击右上角缩小图标；
- 没有任何烦人的“您确定要离开吗？未保存内容将丢失”二次确认弹窗（因为数据已经实时写入本地 IndexedDB）；
- 画布收回主页，刚才写的文字整整齐齐留在小框中。

## 4. 边界防御与异常处理规范

| 异常/边界场景 | 系统防护机制与用户反馈 |
|---|---|
| **网络离线** | - **记录模式**：正常排入本地 IndexedDB 离线队列，Toast 提示“已存入离线队列，联网后自动同步”。<br>- **文章模式**：文章需要分配服务端实体并认领附件，离线时点击拦截并 Toast 提示：“创建文章草稿需要网络连接，请联网后继续”，草稿留在面板内不丢失。 |
| **内容超长拦截** | - **记录模式**：维持 100KB 校验。<br>- **文章模式**：前置拦截 200KB（`MAX_ARTICLE_CONTENT_LENGTH`），超限 Toast 提示：“文章内容超出 200KB 限制”，阻止发包，就地保留文字。 |
| **附件上传进行中** | - 当有图片正在后台切片上传或处理时，主按钮处于 `disabled` 态，防止提早提交导致孤儿附件泄露；工具条展示平稳的上传指示。 |
| **草稿持久化保障** | - `MemoCaptureInput` 扩充 `title?: string`；<br>- 当用户输入了文章标题后即使意外关闭标签页或刷新浏览器，再次打开点全屏，标题与正文依然被 IndexedDB 完整还原。 |
| **移动端虚拟键盘** | - 移动端全屏采用 `dvh`（动态视口高度），底部操作栏随虚拟键盘弹起自适应抬升；<br>- 触控区域最小保持 44x44pt，防止误触。 |

## 5. 多语言规范（i18n Parity）

遵循 8 语言对齐契约，新增键值全部补入 `zh-CN`、`en-US`、`ja`、`fr`、`es`、`ko`、`ru`、`ar`：

```typescript

"composer.fullscreen.open": "全屏写作",

"composer.fullscreen.articleTitlePlaceholder": "文章标题…",
"composer.type.label": "发布类型",
"composer.type.memo": "记录 · 发到时间线",
"composer.type.article": "文章 · 公开可收录",

"composer.article.offlineBlocked": "创建文章草稿需要网络连接",
"composer.article.tooLong": "文章内容超出 200KB 限制",
```
