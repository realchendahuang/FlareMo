# Voice Capture design

FlareMo owns the full product: React/PWA → same-origin Worker → Tencent Cloud or DashScope → browser transcript → existing Memo API → D1/FTS and the configured embedding pipeline. `circleoflife/realtime-context` supplies the reference audio/ASR approach, not another deployed service. There are no new database tables, authentication tokens, Durable Objects, or original-audio attachments in V1.

## Audio and browser lifecycle

`CaptureController` owns the microphone, WebSocket, cancellation signal, reconnect timer, and heartbeat. The UI subscribes to its explicit states; microphone activity and recognition readiness are separate. Start originates from a click. The AudioContext resumes in that gesture, then the permission result is checked against cancellation. Late permission grants are closed. Stop, navigation, logout, pagehide, permission errors, and capture interruption release tracks. In-app navigation shows explicit Continue recording and Stop and leave actions; the latter drains final ASR output and persists the draft before proceeding. Foreground loss stops capture, and reload only offers text recovery.

An AudioWorklet executes a stateful polyphase low-pass resampler and produces 100 ms / 3,200-byte mono 16 kHz signed little-endian PCM frames. The filter uses 96 taps at common 44.1/48 kHz inputs and scales with higher input rates, preserving the transition band and about 1 ms group delay. Integer phase carries across render blocks. Worklet buffers have constant size; frames are transferred to the main thread. ScriptProcessor is a compatibility fallback if worklet initialization fails. Stop immediately releases tracks, flushes the already-captured partial frame (up to 300 ms acknowledgement wait), then asks the Worker to finish ASR. It retains no raw recording.

Audio before service readiness or during a connection gap is deliberately not queued. The UI asks the user to wait before speaking and labels reconnection gaps. Every asynchronous transport boundary has a prospective 64 kB send-queue limit: browser to Worker PCM, Worker to provider PCM, and Worker to browser transcript events. A slow peer therefore causes a retryable disconnect instead of unbounded buffering. Retryable network/capacity failures back off 1, 2, 4, 8, 15, 15 seconds before ending with editable text. Authentication, quota, configuration and protocol failures stop immediately, while the browser receives only a generic message and a retry decision. A resumed connection does not reopen the microphone. The browser checks PCM activity and transport heartbeat independently, so silence is not mistaken for a dead microphone.

## Worker and provider boundary

Capture status and WebSocket require Better Auth browser cookies; Authorization headers are rejected. The WebSocket GET also checks the exact configured Origin allowlist. Capability status is not cached and means configured, not that a live upstream recognition request has succeeded. Active sessions are reauthenticated every 60 seconds. Closing either socket cancels the other, including pending provider connections.

After authentication, exact-Origin validation, provider readiness, and a valid upgrade request, Capture applies the deployment's existing Cloudflare Rate Limiter under a distinct `capture` bucket keyed by the authenticated user ID. The default binding permits 30 connection starts per minute per user, which accommodates the bounded reconnect policy while containing reconnect storms and rapid paid-session creation without coupling unrelated users behind one IP. Unauthenticated, cross-origin, unavailable-provider, status, and non-upgrade requests do not consume this bucket. Cloudflare counters are local to the location serving the Worker, so this is an admission-rate guard rather than a strict global concurrent-session counter; V1 intentionally does not add a database lease or Durable Object solely for Capture. See [Cloudflare Rate Limiting bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

The configured-provider factory is shared by status and WebSocket routes. Missing Tencent AppID/SecretId/SecretKey, incompatible model configuration or an unknown provider makes Capture unavailable; it never silently switches providers. Status checks only local configuration and makes no upstream request. Both adapters implement the same ready, audio, sentence, finish and cancellation contract. Provider close/failure and start/finish timeouts fail closed. Worker logs record only a safe failure category and retryability; provider response bodies and credentials are never reflected to the browser.

The Tencent adapter generates a new voice UUID on every connection, signs the fixed upstream host/path and sorted parameters with Worker Web Crypto HMAC-SHA1, and URL-encodes the signature. The signed URL has a five-minute handshake validity and stays server-side; fetch errors are replaced with generic errors to avoid leaking it. Audio starts after Tencent's success acknowledgement. Browser 100 ms frames are coalesced into Tencent's recommended 200 ms / 6,400-byte packets; finish immediately flushes a shorter tail, so buffering stays bounded below 200 ms. Sentence IDs combine voice UUID and result index; only `slice_type=2` confirms a sentence. Stop sends `type=end` and waits for `final=1` after draining any final result, with a ten-second timeout. Abort closes pending or late upgrades. The default realtime model is `16k_zh_en`, VAD is enabled, and no recognition queue retains audio across reconnects. Optional validated Tencent vocabulary IDs or temporary hotword lists are server-only accuracy hints; ambiguous combinations fail configuration readiness. The provider-neutral bridge canonicalizes only the exact provider variants `flaremo`, `flaremore`, `Fla尔莫`, and `flair莫`, all observed in real runs, to the product spelling `FlareMo`; longer ASCII identifiers remain unchanged.

The DashScope adapter obtains a temporary credential per connection, keeps it server-side, and opens the documented Beijing inference endpoint. No module-global cache shares credentials across deployments or key rotations. Its 20-second timeout covers token exchange and WebSocket upgrade only and is detached as soon as the upgrade succeeds, so it cannot terminate a healthy recording later. Run-task must receive task-started before `ready` is emitted. Results are validated, heartbeats ignored, partial/final identity is stable across updates, and `sentence_end` determines finality. Finish-task uses the same UUID and must receive task-finished after the last result before `finished` reaches the browser.

The bridge rejects PCM before ready, unknown/oversized control messages, odd-sized or >6,400-byte PCM frames, and an audio stream exceeding a 64 kB burst / 32 kB per second rate. No provider protocol is accepted from the browser. Missing audio for 15 seconds and the one-hour session bound close the connection. UI text is bounded to 90,000 characters / 4,000 finalized sentences; only the most recent 100 sentences render during capture. Partial-result updates render independently. Final text formatting is append-only, so each confirmed sentence is formatted once instead of rebuilding the complete transcript after every result.

## Text, recovery and persistence

Final sentences are deduplicated by session-qualified provider sentence ID. Partials remain visually separate and are not saved as completed speech. Sentence timestamps in the editable transcript are receipt times; provider-relative offsets also remain in the live controller. Gaps are preserved in the resulting note as an explicit warning.

Existing IndexedDB drafts store a versioned local capture document keyed by authenticated user and tab session: editable text, recording start, duration, tags, visibility, stable creation client ID and gap flag. Final text persists after a 500 ms quiet period; review edits debounce 250 ms. Serialized writes and a deletion barrier prevent an earlier write from reviving a discarded/saved draft. Recovery requires an explicit click, restores the editor, and never activates the microphone. Draft storage failure is visible and does not block saving through the Memo API. Browser storage clearing and closing the tab session can make drafts unavailable; local drafts are not server backups.

The draft store remembers whether the current capture was ever persisted or recovered. A failed delete remains blocking when a known draft exists, preventing an old recovery copy from surviving a successful server save. If IndexedDB was unavailable for the entire capture and no draft was ever accepted, deletion failure is non-blocking: the ordinary Memo save completes and navigates normally because there is no confirmed local copy to clean up.

Review defaults to private and always includes the `voice` tag. Save uses the existing `createMemo()` with `source: voice` and `payload.client_id`; the domain's unique user/client-ID constraint protects retries from duplicate creation. If D1 commits but the create response is lost, the retry returns that same Memo. When the returned content, visibility, and tags exactly match the previous submission snapshot retained by the page, Capture reconciles any newer local values through the existing update API before clearing the draft. A Memo changed elsewhere is never overwritten silently, and its local recovery copy remains available. Successful save invalidates memo/tag caches and opens the normal detail page. FTS, permission checks, export, archiving, and optional embeddings use the existing memo services.

## Evidence and remaining acceptance

Final sentences use append-only storage with an explicit version signal for React updates, so long recordings do not copy the full sentence history on every result.

Automated tests exercise provider ready/final sequencing, bridge authentication and cleanup, prospective send-queue bounds in both directions, frame bounds, microphone cancellation, retry limits, 44.1/48 kHz resampling, synthetic 30-minute PCM processing, a 4,000-sentence ordered/deduplicated transcript boundary, linear append-only transcript formatting, draft ordering and recovery. Browser tests use Chromium's generated microphone and a simulated ASR WebSocket while exercising the real AudioWorklet and real local Worker/D1. The primary flow proves the saved private Memo appears in the timeline, exposes the `voice` tag, is found through the normal UI and tagged API search, and retains `source: voice` in the standard export bundle. A fault-injection flow lets D1 commit the create, drops its HTTP response, edits the retained transcript, and retries; it proves the newest edit is reconciled into exactly one Memo. The browser suite also verifies that foreground loss drains the final sentence and releases the media track, an authenticated-session logout unmounts Capture and releases the track, Screen Wake Lock is held only while the microphone is active, ScriptProcessor produces bounded PCM when AudioWorklet is unavailable, and a capture can still save and search when IndexedDB is unavailable from startup. A browser reconnect test closes the first ASR transport after audio begins, verifies that the same microphone remains active through bounded backoff, resumes final text on a second socket, and persists an explicit transcript-gap warning in the resulting private `voice` Memo. The production Service Worker treats `/capture` as an authenticated app-shell navigation; an executed-worker test proves an online Capture response populates the shell cache and a later offline navigation falls back to it. This only restores the interface and local text recovery because live ASR still requires a network. A separate Playwright WebKit 26.6 check uses the iPhone 15 device profile and browser-provided mock microphone to complete AudioWorklet capture, Stop, Review, private Memo save/search, track release, and mobile overflow checks. It reduces engine-compatibility risk but is not physical-iPhone or installed-PWA evidence.

The isolated live-provider harness additionally passed 303-second and 1,800-second real-time Chromium → AudioWorklet → Worker → Tencent sessions. It reports final-sentence latency from each provider-relative sentence end to the Worker's receipt timestamp. A five-utterance, 30.48-second browser run measured 292 ms P95 and maximum latency, used one WebSocket, saved and searched the Memo, and normalized the newly observed exact `Fla尔莫` provider spelling to `FlareMo`. A separate 24.18-second fixed Chinese reference covered mixed English, a numeral, time, performance, privacy, mobile validation, network switching, and the Stop boundary. Its full browser run used one WebSocket, saved and searched the Memo, measured 82 ms final-sentence latency, and scored one character edit out of 103: 0.97% CER and 1.69% WER, passing a 5% CER gate. The first baseline exposed the exact `flair莫` product-name variant at 4.85% CER; the constrained normalization reduced it without changing longer ASCII identifiers. A caller-supplied reference transcript produces normalized CER/WER and can enforce a maximum CER for repeatable model, vocabulary, and region comparisons. These deterministic synthesized desktop probes are useful regression evidence, not a population accuracy or latency guarantee. They do not measure DashScope accuracy, deployed-region latency, Safari/PWA behavior, physical-phone microphones, calls, lock/unlock, or mobile network switching. Those require actual device acceptance. Deployment and product completion must not be inferred from local desktop evidence.
